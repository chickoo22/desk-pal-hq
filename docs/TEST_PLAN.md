# DeskPal HQ — End-to-End Test Plan

Detailed, feature-by-feature manual test cases covering the full product, derived from the current README and verified against the source (routes in `src/App.tsx`, DB functions and triggers in `supabase/migrations/`).

## How to read this document

Each test case has an ID, a priority, preconditions, steps, and the expected result.

- **Priority:** `P0` = critical path / security (must pass to ship) · `P1` = important · `P2` = edge / polish.
- **Type:** `(+)` positive (happy path) · `(−)` negative (should be blocked/rejected).
- Steps assume the tester performs the action in the browser unless noted.

## Standing test data (set up once)

Create these accounts/entities before running the suites. Reuse the aliases throughout.

| Alias | Role | Notes |
|---|---|---|
| **OWNER** | Platform owner | Allow-listed email, created via `/owner-login` one-time setup |
| **Acme** | Company A | Primary tenant |

# 1. Authentication & Session (AUTH)

### AUTH-01 (+) P0 — Sign up and create a new company
**Precondition:** Signed out. On `/signup`.
**Steps:**
1. Choose "New company".
2. Enter full name, work email, password (≥ 8 chars, not a breached password), company name.
3. Submit.
**Expected:** Account created; user becomes **Admin** of the new company; redirected to `/setup` (setup wizard) because the company has no `setup_completed_at`/`setup_skipped_at`. A `profiles` row, an admin `user_roles` row, and a `companies` row exist.

### AUTH-02 (+) P0 — Sign up by joining with an invite code
**Precondition:** A valid, unused, unexpired invite code exists for Acme (generated by HR/Admin). Signed out.
**Steps:**
1. On `/signup`, choose "I have an invite code".
2. Enter name, the email the invite was issued to, password, and the invite code.
3. Submit.
**Expected:** Account created and attached to Acme with the invited role. If a matching `pending_employees` record exists for that email, the person's imported details/manager/shift are applied to their profile automatically (`link_pending_employee`). Redirected to dashboard (or `/join` if no active company got set).

### AUTH-03 (−) P0 — Sign up with an invalid / used / expired / inactive invite code
**Steps:** On `/signup` (invite mode) enter, in turn: a random invalid code; an already-redeemed code; an expired code (> 30 days old); a code for a deactivated company.
**Expected:** Each is rejected **before** account creation, with a specific, plain-English message explaining which case it is and the next step. No account is created.

### AUTH-04 (−) P1 — Password below minimum length
**Steps:** On `/signup` enter a 7-character password.
**Expected:** Blocked with a clear message; minimum is 8.

### AUTH-05 (−) P1 — Breached password rejected
**Steps:** On `/signup` enter a known-breached password (e.g. `Password123`).
**Expected:** Rejected by the HIBP breach check with guidance to choose another.

### AUTH-06 (+) P0 — Log in with valid credentials
**Precondition:** EMP_A1 exists. On `/login`.
**Steps:** Enter EMP_A1 email + password, submit.
**Expected:** Signed in, lands on role-aware dashboard. Previous cached page data is cleared (no other account's data visible).

### AUTH-07 (−) P0 — Log in with wrong password shows generic error
**Steps:** Enter EMP_A1 email with a wrong password.
**Expected:** Generic error ("invalid credentials" style) that does **not** reveal whether the account exists.

### AUTH-08 (−) P0 — Account lockout after repeated failures
**Steps:** Fail login for the **same email** 5 times within 15 minutes.
**Expected:** That email is locked for 15 minutes; further attempts (even with the correct password) are refused during the lock. After 15 minutes, or after a successful login once unlocked, the counter resets.

### AUTH-09 (+) P1 — Successful login resets the failed-attempt counter
**Steps:** Fail login 3 times, then log in successfully, then fail again.
**Expected:** The earlier 3 failures do not count toward the lockout threshold after the successful login.

### AUTH-10 (+) P0 — Password reset request and completion
**Steps:**
1. On `/login` use "Forgot password", enter EMP_A1 email.
2. Open the reset link from email, set a new valid password.
**Expected:** Reset email sent (generic confirmation regardless of whether the email exists); the reset link lets the user set a new password but does **not** silently sign them in; the link expires after its window and cannot be reused.

### AUTH-11 (−) P1 — Password age expiry forces reset
**Precondition:** A user whose password is > 90 days old.
**Steps:** Attempt to use the app.
**Expected:** Redirected to `/reset-password?expired=1`; cannot use workspace routes until the password is changed. (Owner support sessions are exempt.)

### AUTH-12 (+) P1 — Change password requires current password
**Steps:** As EMP_A1, in profile/settings, change password; enter current password + new password.
**Expected:** Change succeeds only when the current password is correct; wrong current password is rejected.

### AUTH-13 (−) P1 — Session inactivity timeout
**Steps:** Sign in, leave the tab idle for > 30 minutes, then act.
**Expected:** Session expired; user signed out automatically and sent to `/login`.

### AUTH-14 (−) P1 — Absolute session cap
**Steps:** Stay signed in and active for > 12 hours total.
**Expected:** Signed out automatically at the 12-hour cap.

### AUTH-15 (+) P1 — Logout clears cached data
**Steps:** As EMP_A1 view attendance/leave, log out, then log in as EMP_A2.
**Expected:** None of EMP_A1's records flash up under EMP_A2; cache is cleared on sign-out and sign-in.

### AUTH-16 (−) P0 — Signed-out access to protected routes
**Steps:** While signed out, navigate directly to `/`, `/employees`, `/payroll`, `/owner`.
**Expected:** Redirected to `/login` (or `/owner-login` for `/owner`). No protected content renders.

# 10. Leave Application & Approval (LV) — core flow

> State model (verified in triggers): a request carries `manager_status` and `hr_status`, each `pending → approved | rejected`, plus an overall `status` that can be `cancelled`. Manager is stage 1, HR is stage 2.

### LV-01 (+) P0 — Employee applies for leave
**Precondition:** EMP_A1 reports to MGR_A; a leave type is enabled for EMP_A1 with available balance.
**Steps:** EMP_A1 on `/leave` applies for Casual leave, future dates, with a reason.
**Expected:** Request created (`manager_status=pending`, `hr_status=pending`); balance shows the days as **pending**; MGR_A receives a "New leave request" notification. EMP_A1 sees the request under their own requests.

### LV-02 (+) P0 — Manager approves → routed to HR
**Steps:** MGR_A on `/approvals` approves EMP_A1's request.
**Expected:** `manager_status=approved`. EMP_A1 notified "Manager approved your leave … sent to HR". All HR/Admin users notified "Leave awaiting HR approval". The request is still **not** finally approved.

### LV-03 (+) P0 — HR approves → fully approved
**Steps:** HR_A on `/approvals` approves the (manager-approved) request.
**Expected:** `hr_status=approved`; overall status approved; EMP_A1 notified "Leave approved"; the days move from pending to consumed in the balance; the leave shows on the attendance calendar and blocks check-in (ATT-04) for full days.

### LV-04 (−) P0 — Manager rejects (flow ends at stage 1)
**Precondition:** Fresh pending request from EMP_A1.
**Steps:** MGR_A rejects with a note.
**Expected:** `manager_status=rejected`; EMP_A1 notified "Leave rejected by manager" including the note; the request does **not** reach HR; pending days are returned to the balance; no HR notification to approve.

### LV-05 (−) P0 — HR rejects after manager approval (flow ends at stage 2)
**Precondition:** Request with `manager_status=approved`, `hr_status=pending`.
**Steps:** HR_A rejects with a note.
**Expected:** `hr_status=rejected`; EMP_A1 notified "Leave rejected by HR" with the note; pending days returned to balance; leave does not appear as approved anywhere.

### LV-06 (+) P1 — HR/Admin cancels an approved leave; balance reallocated
**Precondition:** A fully approved leave for EMP_A1.
**Steps:** HR_A cancels it (optionally with a note).
**Expected:** `status=cancelled`; `manager_status`/`hr_status` set to cancelled; the days are **returned** to EMP_A1's balance; because the canceller ≠ the employee, EMP_A1 is notified "Leave cancelled … days returned" with the note.

### LV-07 (+) P1 — Employee cancels own pending request
**Steps:** EMP_A1 cancels their still-pending request.
**Expected:** Allowed (self-cancel of pending); pending days returned; no "cancelled by someone else" notification (actor = owner).

### LV-08 (−) P1 — Overlap prevention
**Steps:** EMP_A1 applies for dates overlapping an existing pending/approved leave.
**Expected:** Rejected with an overlap message (trigger-enforced).

### LV-09 (+) P1 — Half-day leave
**Steps:** EMP_A1 applies for a half-day (single date, day portion = half).
**Expected:** 0.5 day deducted; a half-day spanning two dates is rejected.

### LV-10 (−) P0 — Manager cannot approve their own leave (self-approval block)
**Precondition:** MGR_A applies for leave (MGR_A also reports to someone, or is HR-approved).
**Steps:** MGR_A tries to approve their own request on `/approvals`.
**Expected:** Blocked in the database; MGR_A cannot self-approve.

### LV-11 (−) P0 — Manager sees only direct reports' requests
**Precondition:** EMP_A3 does **not** report to MGR_A.
**Steps:** MGR_A opens `/approvals`.
**Expected:** EMP_A1/EMP_A2 requests appear; EMP_A3's do not. MGR_A cannot approve EMP_A3.

### LV-12 (−) P1 — Apply for a leave type disabled for the employee
**Precondition:** HR disabled "Sick" for EMP_A1 (LT-05).
**Steps:** EMP_A1 opens the apply form.
**Expected:** "Sick" is not selectable for EMP_A1.

### LV-13 (−) P1 — Apply exceeding available balance
**Steps:** EMP_A1 applies for more days than available.
**Expected:** Rejected with an insufficient-balance message (balance check trigger).

### LV-14 (+) P1 — Comp-off grant varies per employee
**Steps:** MGR_A/HR grants EMP_A1 comp-off days for overtime; grant a different amount to EMP_A2.
**Expected:** `comp_off_grants` recorded per person; balances reflect the individual amounts; EMP_A1 can then apply using comp-off (if enabled).

### LV-15 (+) P1 — Yearly leave calendar views
**Steps:** On `/leave`, open the yearly calendar; toggle "My leave" vs "Company"; change the year.
**Expected:** Holidays, weekly offs, and approved leave render for the selected mode/year; "Company" mode shows only public approved leave.
